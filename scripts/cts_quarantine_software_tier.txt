# OpenXR CTS — SOFTWARE-TIER quarantine list                         (#1525 / #1523)
# =============================================================================
# Tests excluded BY NAME when the CTS runs against Mesa's software rasterizers
# (llvmpipe / lavapipe) on a GitHub-hosted runner with no GPU.
#
# This file is the ONE place the software tier's exclusions live. It is passed
# to scripts/run_cts.ps1 via -QuarantineList (Windows) and to
# scripts/run_cts.sh via --quarantine-list (Linux, #1527), and ONLY on the
# software tier:
#
#   * the PR lane (d3d11/d3d12 on WARP)              -> not passed
#   * the self-hosted, real-GPU tier (#1526)         -> not passed
#   * a real-GPU Linux box (run_cts.sh without --software) -> not passed
#      run_cts.sh REFUSES to apply the list unless --software is also set, so
#      "real GPU + quarantine" is not a state a typo can reach.
#
# CROSS-PLATFORM BY CONSTRUCTION. The single entry below is a property of
# rasterizing on the CPU, which is equally true of Windows llvmpipe/lavapipe
# and of Linux lavapipe under Xvfb — so both software tiers read this same
# file rather than forking a near-identical one. An entry that is true on only
# one OS does not belong here; say so in a comment and gate it there instead.
#
# so an entry here can never silently hide a defect on a tier that has real
# hardware. That is the point: a test quarantined *everywhere* is a defect
# nobody is looking at. If something has to be excluded on real hardware too,
# it belongs in an issue and in the default TestSpec, not in this file.
#
# FORMAT
#   One Catch2 test-case NAME per line. Everything from a leading '#' to the
#   end of the line is a comment; blank lines are ignored. Names are appended
#   to the test spec as `~name` filters (Catch2 ANDs patterns inside one
#   filter, so there is deliberately NO comma — see run_cts.ps1).
#
# RULES FOR ADDING AN ENTRY
#   1. State the reason and link an issue. No bare names.
#   2. The reason must be a property of the SOFTWARE ENVIRONMENT (no GPU, no
#      timer/scheduling headroom, a rasterizer that is 100x slower), not a
#      property of the runtime. If the runtime is wrong, fix the runtime.
#   3. Re-check entries when the Mesa pin or the runner image moves. An entry
#      that would now pass is worse than no entry.
#
# NOT A PLACE TO PUT THE VULKAN ARMS.
# Their history is the worked example of rule 2. They were blocked at
# vkCreateDevice (the runtime required the Win32 external
# memory/semaphore/fence trio unconditionally; no Windows software ICD has it
# — lavapipe and SwiftShader are FD-only, Mesa dzn has memory+semaphore but no
# external_fence at all), and then by a SIGSEGV in SessionState. Neither was
# ever a candidate for this file: a device-creation failure takes out EVERY
# session-creating test rather than a nameable few, and a crash is not a test
# name — listing either would have been renaming a blocker as a flake. All
# three are now fixed (#1539, #1542 via #1550, #1558 via #1560) and BOTH ARMS
# GATE as of the all-arm zero-red run 35458623141 — on a run, not on "no known
# blocker". Neither needs an entry here; if one ever does, it has to clear
# rule 2 on its own evidence.
# See docs/roadmap/cts-windows-handoff.md § Software-rasterizer tier.
#
# WHY THERE IS EXACTLY ONE ENTRY.
# The first software-tier runs were allowed to fail honestly before anything
# was named here; pre-populating from guesswork would have quarantined tests
# that pass and hidden the ones that do not. The full non-interactive OpenGL
# suite then ran to completion on llvmpipe and came back with ONE red
# assertion out of 27515 — the entry below, and nothing else.

# Timed_Pipelined_Frame_Submission — frame-pacing overhead on a CPU rasterizer.
#   Evidence: run 35433846568 (workflow_dispatch on main, graphics=opengl
#   scope=full software_gfx=on, CTS 1.1.63.0) — 27515 assertions, 1 failure,
#   0 errors, 42 skipped. The one failure is
#     REQUIRE( timingResults.GetOverheadFactor() < 0.5 )
#     with expansion: 1.08553478400000003 < 0.5
#   i.e. an "Overhead score : 108.6%" against the CTS's hard 50% cap
#   (test_FrameSubmission.cpp:465). Overhead is
#   (avg frame time / predicted display period) - 1, so it measures how much
#   longer a frame takes than the runtime predicted — on llvmpipe every frame
#   is rasterized on the CPU, on a 2-vCPU hosted runner, against a display
#   period the runtime predicts as if a GPU were scanning out. The same arm on
#   a real GPU has 0 unexpected failures (#1523), which is the property that
#   makes this environmental rather than a runtime defect.
#   Issue: #1523 (arm gating) / #589 (this test's timer sensitivity on Windows).
#   Re-check: whenever the Mesa pin or the windows-2022 image moves, and drop
#   this line the moment the hosted runner can hold the frame budget.
Timed_Pipelined_Frame_Submission

# COST OF THAT ENTRY, STATED OUT LOUD.
# cts.yml's "Report frame-timing metrics" step scrapes this test's printed
# overhead numbers to trend the runner's frame timing (#589). Excluding the
# test by name means the software tier prints "No Timed_Pipelined_Frame_Submission
# metrics in console log" instead of a percentage — the scrape is blind exactly
# where the timing is worst. That is a deliberate trade: the alternative is an
# opengl arm that can never gate, which buys nothing, because a known-red arm
# is one nobody reads. The real-GPU tier (#1526) does not pass this file, so it
# keeps both the test and the trend line.
