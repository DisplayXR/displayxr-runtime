# ADR-064: Component catalog and third-party trust

**Status:** Proposed (2026-11-20). The direction below is decided by the project lead,
including the review decisions of 2026-11-20 (every installable binary is signed; signers are
matched by certificate subject; § Decided in review). The schema details and the step order
are proposed for review. Implemented so far: the generator's
schema-2 derivation (`scripts/gen_catalog.py --out-v2`) and, in `dxr-get`, steps 2 and 3 of the
plan below (PR #2734). Nothing publishes schema 2 yet, so `dxr-get` falls back to schema 1. Builds on epic [#2702](https://github.com/DisplayXR/displayxr-runtime/issues/2702)
(self-fetching installers), applies [ADR-054](ADR-054-component-model.md) (the component
model) and its N4b provenance gate to distribution, and triggers ADR-054 N5 (licensing state
for every class). Related: [ADR-019](ADR-019-vendor-plugin-aux-boundary.md),
[ADR-020](ADR-020-plugin-abi-compatibility-policy.md),
[ADR-038](ADR-038-android-vendor-plugin-ships-in-the-runtime-apk.md),
[ADR-053](ADR-053-conversion-providers.md),
[ADR-063](ADR-063-input-provider-device-abi-hardening.md). Specs:
[component-catalog.md](../specs/runtime/component-catalog.md) (schema 2 is specified there),
[dxr-get.md](../specs/runtime/dxr-get.md),
[plugin-discovery.md §4.3](../specs/runtime/plugin-discovery.md).

## In one paragraph

DisplayXR components are separately installable by design (ADR-019, ADR-054), but the only
way to find and install one today is to know its repository. Epic #2702 built a signed index
of three first-party Windows installers and a tool, `dxr-get`, that fetches and verifies
them. This record generalises that into the **DisplayXR Catalog**: a public registry of
signed manifests for components from first and third parties, one install engine with two
front ends, and no commerce. Publishers host their own binaries and sell their own licences;
DisplayXR lists, verifies and installs. A third-party binary earns load-time trust through
the catalog, and the provenance gate stays the place where trust is enforced.

## Context

### What #2702 built

| Piece | Where | What it does |
|---|---|---|
| Catalog, schema 1 | `https://updates.displayxr.org/catalog/v1/stable.json` (+ `.sig`), generated by `scripts/gen_catalog.py`, published by `.github/workflows/publish-catalog.yml` | One Ed25519-signed JSON document listing `runtime`, `leia_plugin` and `browser`: the `versions.json` pin, a Windows installer (size, SHA-256, Authenticode signer, two URLs, silent arguments, the registry value that holds the installed version), a runtime floor, and EDID / registry detection rules for the display plug-in |
| `dxr-get.exe` | `src/xrt/targets/get/`, spec `docs/specs/runtime/dxr-get.md` | Standalone Windows tool: `plan`, `ensure-for`, `fetch`, `install`, `detect`, `catalog`. Verifies the catalog signature, expiry and serial, then size, SHA-256 and Authenticode signer of every payload |

### Its limits

Read from the code and the two specs on `main`:

- **Windows only.** `dxr-get` is Win32 (WinHTTP, `WinVerifyTrust`, the registry). Schema 1
  has one platform block, `windows`.
- **One first-party document.** The generator builds the whole catalog from `versions.json`
  and a hard-coded `COMPONENTS` list. There is no way for anyone else to add an entry.
- **Three components, by name.** `dxr-get` knows `runtime`, `leia_plugin` and `browser` by
  string: labels, default registry paths and the whole plan (`make_plan`) are written around
  those names, and detection is evaluated for `leia_plugin` only. The catalog says nothing
  about component class, registered id or class ABI.
- **A compiled-in signer.** A payload installs only if its Authenticode leaf CN equals the
  catalog's `signer` **and** an entry of `k_trusted_signers` in `get_main.c` (one entry
  today). A second publisher needs a new `dxr-get` build in every installer that embeds one.
- **No uninstall, no update, no inventory.** `install` does nothing when the installed
  version is at or above the catalog's; nothing removes a component, lists what is
  installed, or reports what is out of date. `ensure-for` is deliberately not an updater.
- **External prerequisites are invisible.** A provider that needs a vendor service or a
  vendor model runtime cannot say so, and the user learns it from a provider state after
  install.

### Why now

Three things need a catalog at the same time: third parties are building providers of every
class (ADR-054 admitted the fourth class and fixed the contract the fifth would follow); the
first paid provider is real, so ADR-054 N5 can no longer wait; and the vendor-neutral bundle
cannot keep carrying vendor providers if a vendor is free to stop bundling one.

## Decision

### 1. Three layers, and no commerce

1. **Catalog.** Signed manifests in a public registry repository. Each item names its
   publisher, its class and registered id, its compatibility range, its per-platform assets
   by URL and hash, its licence terms and its prerequisites. **Publishers host their own
   binaries; DisplayXR hosts none.** Reason: hosting makes DisplayXR a distributor of code it
   did not build, with the storage, takedown and export obligations that follow, and it
   gives nothing a hash-pinned URL does not.
2. **Install path.** `dxr-get` is the one engine. `displayxr-cli catalog …` and a Dashboard
   **Catalog** tab are front ends over it, following ADR-051: the CLI is the logic, the
   Dashboard renders what the CLI returns. Reason: one place verifies signatures and runs
   installers, so there is one place to audit.
3. **No commerce.** DisplayXR handles no payment and takes no cut. Reason: a payment path
   would put DisplayXR between a vendor and its customers, make the runtime's neutrality
   depend on a revenue share, and bring payment, tax and refund duties the project has no
   reason to carry.

### 2. Item kinds

| Kind (`class`) | What it is | How it is installed |
|---|---|---|
| `display_processor` | ADR-019 / ADR-054 class | installer, registers under `DisplayProcessors` |
| `input_provider` | ADR-034 class | installer, registers under `InputProviders` |
| `conversion_provider` | ADR-053 class | installer, registers under `ConversionProviders` |
| `tracking_provider` | ADR-054 §4.1 class | installer, registers under `TrackingProviders` |
| `workspace_controller` | process contract over IPC (ADR-016) | installer, registers under `WorkspaceControllers` |
| `companion` | a pose consumer in its own process (ADR-054 §4.3) | installer, registers under `PoseConsumers` once N8 lands |
| `app` | an application | **link-out**: the catalog points at the publisher's page or store listing |
| `sdk` | an SDK or engine plug-in | **link-out** |
| `runtime` | the trunk itself | first-party only; what every other item's floor refers to |

The first-party DisplayXR Browser is an `app` with a fetchable asset, because installers
already fetch it through `dxr-get`; a third-party `app` is link-out only.

**DXR Play game profiles are not catalog items.** A profile loads into the game's process,
not into the runtime, so it lives in a separate trust domain: the provenance gate never sees
it, the class conformance run does not apply to it, and listing it here would suggest a
vetting that did not happen. Profiles keep their own distribution.

### 3. Schema 2

Specified field by field in
[component-catalog.md § Schema 2](../specs/runtime/component-catalog.md#schema-2). In short:

```json
{
 "schema": 2, "serial": 0, "generated": "…", "expires": "…", "channel": "stable",
 "publishers": { "<publisher>": { "name": "…", "signers": { "windows-x64": [ { "kind": "authenticode", "subject_cn": "…" } ] } } },
 "items": [ {
   "id": "…", "class": "…", "registered_id": "…", "publisher": "<publisher>", "tier": "listed|verified",
   "version": "…", "abi": { "<class>": { "min": 0, "max": 0 } }, "runtime": { "min": "…", "max": "…" },
   "assets": { "<platform>": { "file": "…", "size": 0, "sha256": "…", "urls": ["…"],
                               "signature": {}, "installer": {}, "installed": {}, "uninstall": {} } },
   "provenance": {}, "license": {}, "requires": [], "detect": [], "links": {}
 } ]
}
```

It is a **separate document at a separate URL** (`catalog/v2/stable.json`). Deployed
`dxr-get` builds accept `schema == 1` only and treat any other value as *offline*, so
changing the existing file's schema number would stop every installer that embeds one.
Schema 1 keeps being published unchanged for as long as those builds are in service.

### 4. Trust model

**Every listed installable binary is signed.** An item with a fetchable asset is listed only
if the installer and the component binaries it installs are signed by a signer delegated to
its publisher. There is no unsigned, hash-pinned-only form. Reason: an unsigned binary can
pass the load gate only through an allowlist row, and **`dxr-get` does not write
`Trust\Allowlist` rows** — the #2702 rule stands. A catalog that listed unsigned binaries
would either break that rule or list things that install and then refuse to load.

**Two tiers.**

| Tier | Requirements | What the user sees |
|---|---|---|
| **Listed** | manifest validated; assets signed by the publisher's delegated signer; hashes pinned. Not conformance-tested | listed and installable, with a one-line statement that DisplayXR has not tested it |
| **Verified** | everything Listed requires, plus a recorded class conformance run (ADR-054 N4: selected, one round trip, `Enabled=0` falls back, `Preferred` wins, an ABI-mismatch fixture is rejected) against a named runtime version | listed and installable, marked Verified |

**The provenance gate stays the load-time enforcement point.** The catalog does not load
anything and grants nothing at load time by itself. A catalog-installed binary reads `signed`
at the gate, as any signed binary does today (plugin-discovery.md §4.3). What the catalog
adds is the missing half, *who* is expected to have signed it: the item's publisher and that
publisher's delegated signers. That is how a third-party binary earns signer trust: at
install, the engine refuses a payload whose signer is not delegated to its publisher. The
gate may later record whether the signer it sees at load matches the catalog's; it does not
refuse on a mismatch in this ADR, because pinning publishers at load is a separate decision
with its own failure modes (step 2 lists it as an open point). The allowlist keeps its
current writers and its current purpose: the runtime installer's own unsigned reference
builds, a vendor installer's own rows, and the dev lane.

**Signer identity.** A signer is named by the **certificate subject**, exactly as schema 1
does (the Authenticode leaf's subject CN), declared per publisher in the signed index. A
possible later tightening is to also pin the subject organisation or the issuer. It is
recorded and not adopted now: a subject CN is not unique across certificate authorities, so
pinning more would resist a look-alike certificate better, but a publisher's renewal or
change of authority would then break installs until the registry is updated.

**Per-publisher signers replace the compiled-in list.** Today the set of acceptable
Authenticode signers is compiled into `dxr-get`. In schema 2 the signed index carries
`publishers.<id>.signers.<platform>`, and a payload is accepted only when its signature
matches a signer delegated to *its own* publisher. One publisher's signer cannot vouch for
another publisher's item. `dxr-get` keeps exactly one thing compiled in: the catalog root
keys.

**Key rotation.**

| Key | Rotation | Revocation |
|---|---|---|
| A publisher's signer | a registry pull request adds the new signer next to the old one; the next index carries both; the old one is removed once no listed asset uses it. No `dxr-get` release | remove the signer from the index: every client that fetches a newer index refuses that signer's payloads. The 30-day expiry bounds how long an offline client can act on the old index. `revoked` (asset digests) blocks a specific bad build while the signer stays |
| The catalog root key | schema-2 clients compile in **two** keys from their first release: the active key and a standby key whose seed is kept offline and never loaded into CI. Rotation is switching the CI secret to the standby and compiling in a new standby in the next release, so it never waits on a client rollout | as schema 1: a client build without the key. The standby key is what makes this fast, because clients already trust the replacement |

A catalog signature proves the index is the registry's; it does not prove a publisher is
honest. What the registry checks before listing is in the spec (§ Registry rules).

### 5. Licence model

**Install is always free and anonymous.** No account, no key and no payment is needed to
fetch or install any item. Only the licence is gated, and it is gated by the vendor, inside
the vendor's plug-in. Reason: the install path stays one path for free and paid items, the
catalog never learns who installed what, and a paid plug-in that is installed but unlicensed
behaves like any provider that cannot serve.

- **State.** A plug-in reports `licensed`, `trial`, `expired` or `unlicensed`, a message and
  a purchase URL through an **append-only slot**, the pattern `describe_settings` used: a new
  slot at the end of each class's vtable, gated by `struct_size`, announced by a feature
  macro, no ABI bump (ADR-020). A plug-in without the slot has no licence to report and is
  treated as free.
- **Source and expiry.** The state carries two optional facts: a `source`, saying where the
  entitlement comes from (`hardware`, `key`, `trial` or `oem`), and an `expiry` time.
  **`licensed` with `source = hardware` is a first-class state**: the connected display
  entitles the user, with no purchase, no key and no click, and the Dashboard shows
  "Included with your display" instead of a Buy / Activate action. `oem` is the same idea
  for an entitlement that came with the machine. `expiry` lets the Dashboard say when a
  trial or a term licence ends before it does. The catalog manifest declares which sources
  an item may use, so a front end can say "included with supported displays" before install;
  what is true on a given machine still comes only from the plug-in.
- **The gate lives in the vendor's binary.** Any hardware or entitlement check is made
  inside the vendor's own binary. It is never made by the runtime, and never by a public
  adapter that sits between the runtime and a vendor's code. The runtime carries what the
  plug-in reports and acts on it (shows it, falls through); it does not decide it. "No DRM
  in the runtime" is a stated principle of this record, not a current limitation.
- **Fall-through.** An unlicensed provider declines, and selection falls through to the next
  candidate. Conversion providers already do this (`UNLICENSED` falls through,
  conversion-provider-discovery.md §4); the same rule now holds for every class.
- **Buy / Activate.** The Dashboard shows one uniform action for any item whose state is not
  `licensed`. It opens the **vendor's** checkout in the user's browser. DisplayXR never sees
  the transaction.
- **Activation by deep link.** The Dashboard starts an activation: it creates a single-use
  nonce bound to one item and passes it to the checkout URL. The vendor's page returns with
  `displayxr://activate?item=…&nonce=…&token=…`. The handler delivers the token **only to
  the plug-in with that pending nonce**, and treats it as opaque: not parsed, not logged, not
  stored by the runtime. A link with no pending nonce does nothing, which is what keeps an
  arbitrary web page from pushing data at a plug-in.
- **Activation by key.** The user pastes a key, stored through the settings contract
  (ADR-054 decision 7) with a new setting type, `secret`: written like any setting, never
  returned by `options`, `status`, logs or the Dashboard (they show *set* / *not set*).

### 6. External prerequisites

`requires` gains kind `external`, for something DisplayXR does not ship: a vendor tracking
service, a vendor model runtime. Two forms are supported, and the publisher chooses:

1. **Declared and detected only.** The manifest names the prerequisite, gives detection
   rules and a link. DisplayXR reports met or unmet before install and installs nothing.
2. **Declared with its own installer asset.** A proprietary prerequisite may carry an asset
   in the manifest: URL, SHA-256, size and signer, the same fields as an item asset, signed
   by a signer delegated to the same publisher. The engine then installs it **in order,
   before the item**, only when detection says it is absent, and never to upgrade one that
   is present. Its download size is added to the item's and **shown before the user
   commits**.

Reason for keeping detection-only as a full form: these prerequisites have their own
licences and update channels, and silently installing or upgrading one can break other
software on the box that depends on it (#2702 already has this rule for the SR platform:
fetched only when missing, never upgraded on its own). Either way the front ends show an
unmet prerequisite before install, instead of after.

### 7. Default converter

The runtime installer and the bundle pull the **open conversion provider** by default. "Convert
to 3D" must not disappear on a machine whose display vendor no longer bundles a converter;
with the open provider present, a vendor converter is an upgrade selection falls back from,
not the only candidate (ADR-042, ADR-053).

### 8. The bundle becomes catalog-driven

Direction recorded here; implementation is out of scope for this ADR's first steps.

- The bundle / runtime installer shows a **checkable component list populated from the
  signed catalog**, and **downloads** the chosen components from their publishers' release
  URLs instead of carrying them.
- **Pre-ticked:** a display processor whose detection rule matches this machine's hardware
  (EDID → display processor), and a recommended set that includes the open conversion
  provider.
- **The vendor-neutral bundle stops carrying vendor providers.** A display processor is
  offered, pre-ticked from detected hardware; it is not embedded.
- **Advantage:** the installer can check whether the installed component is already the same
  version and hash and skip the download.
- **Cost:** it needs a network connection. The installer therefore **says so up front**,
  before the user commits, and handles no connection clearly: it installs what is embedded
  (the runtime core), reports what was skipped, and says how to get it later
  (`displayxr-cli catalog install <id>` or the Dashboard's Catalog tab).
- **The offline full bundle stays** for OEM and air-gapped installs.

What `dxr-get` already covers for this, verified in `get_main.c`, `get_http.c`,
`get_detect.c` and `dxr-get.md`:

| Need | Today | Missing |
|---|---|---|
| Detect hardware | `detect` reads every present monitor's EDID and evaluates the catalog's `edid` and `registry_dword_min` rules, with a confidence level | rules are evaluated for `leia_plugin` only; needs "which items match this machine", for any item |
| Compare versions | installed version is read from the registry value the catalog names; `install` does nothing at or above the catalog version; never downgrades | components that register a `Version` on their class row but have no installer key; inventory of everything installed |
| Same-hash skip | a downloaded installer is cached under `%ProgramData%\DisplayXR\Downloads\<sha256>-<file>` and reused when its hash matches | nothing records which asset hash is *installed*; the install receipt (step 3) does |
| Verify | **every** payload: a complete file of the catalog's size, SHA-256 equal to the catalog's, then Authenticode chain and signer CN. A mismatch discards the file and exits 21. The hash check has no override | the same check on every asset of an item, with the signer taken from the catalog's publisher delegation instead of a compiled-in list |
| Resumable download | `Range` resume of a `.part` file (restarting from zero when the server ignores the range), bounded retries, fallback to the second URL. This is what makes a large asset practical | progress output a setup UI can render |
| Several assets for one item | one asset per component | an item plus the installer assets of its external prerequisites (§6): each resumed and verified on its own, all fetched and verified before the first installer runs, total size known up front |
| Plan before acting | `plan --json` (state, installed, target, size, reason per component) | a plan for a *selection* of items rather than "the prerequisites of X" |
| No connection | an unreachable, expired or unparsable catalog is exit 10, and nothing is installed | a cheap "is the catalog reachable" answer for the up-front notice, and a report of what was skipped |
| Service handling | everything is downloaded and verified first; the service and its satellites stop once, installers run runtime-first, the service starts once | unchanged |

### 9. Platforms

- **Android is listing-only** (ADR-038): the vendor plug-in ships inside the runtime APK and
  nothing is installed separately, so an Android asset is a link, never an installer.
- **The POSIX install engine is a later step.** Until then macOS and Linux items are listed
  with their assets and installed by the user from the publisher's `.pkg` / `.deb`.

## What is deliberately not done

- No payment, no revenue share, no accounts, no telemetry on installs.
- No hosting of third-party binaries.
- No background update and no scheduled network traffic: the #2702 rules that protect
  deployed units all stay. Nothing changes on a box until someone runs an installer or asks
  for an install; a stale catalog never blocks anything already installed.
- **No DRM in the runtime.** The runtime carries a licence *state* and an opaque token. Any
  hardware or entitlement gate lives inside the vendor's own binary, never in the runtime
  and never in a public adapter (§5).
- No rating, review or ranking system.
- No game profiles (§2).
- No unsigned installable items, and no allowlist rows written by the install engine (§4).
- No load-time refusal on a publisher mismatch (§4), and no change to what the provenance
  gate enforces.

## Consequences

- A third party can ship a provider without DisplayXR building, hosting or re-signing it,
  and a user can find and install it without knowing its repository.
- `dxr-get` stops knowing component names. Its table, its plan and its trusted signers
  become data, so a new item or publisher needs a registry change, not a tool release.
- Two catalog documents are published side by side for a while. The serial rule needs care:
  both are generated in the same run with the same serial, and schema-2 clients keep their
  rollback serial in a separate value (spec § Compatibility).
- The registry is a new thing to run: a repository, validation CI, a review rule, a signing
  job, and a policy for delisting.
- The allowlist does not change: `dxr-get` writes no rows, and every catalog-installed
  binary passes the gate on its signature. A publisher without a code-signing certificate
  cannot be listed with a fetchable asset; it can be listed as a link-out.
- Every class gains licence vocabulary (ADR-054 N5), and the settings contract gains a type.
- The bundle depends on the network by default. The offline bundle remains the answer for
  machines without one.
- Trade-off accepted: Listed items are installable without conformance testing. The
  signature, the tier label and the unchanged load gate are the protection, not a listing
  ban; a ban would send third parties back to hand-distributed installers the catalog cannot
  see at all.
- Trade-off accepted: requiring signatures raises the cost of entry for a small publisher.
  It is the price of keeping one trust path.

## Decided in review (2026-11-20)

- **Every listed installable binary is signed; `dxr-get` writes no `Trust\Allowlist` rows.**
  An earlier draft proposed an unsigned tier admitted by engine-written allowlist rows. It
  is dropped, and with it the tier name it used. The tiers are Listed and Verified (§4).
- **Signers are matched by certificate subject**, declared per publisher in the signed
  index. Organisation / issuer pinning is a possible later tightening (§4).
- **Licence `source` and `expiry`, and installer assets on external prerequisites, stay in**
  (§5, §6).

## Open questions

Left open for the project lead:

1. **Conformance ownership for hardware-dependent classes.** Who runs the Verified
   conformance run, and on what hardware, for a class that needs a device (a display
   processor's panel, a tracked input device)? Self-attested by the publisher with a
   report, or run by DisplayXR?
2. **Registry governance.** Where the repository lives, who may approve a new publisher or
   a new signer, and the delisting policy.
3. **First-party tier recording.** The generator emits no `tier` because no conformance
   record exists for the first-party items yet, so they are Listed. Should a run be recorded
   for each, so they are Verified, before schema 2 is published?
4. **The `companion` kind** depends on the pose-consumer registration (ADR-054 N8), which
   is not designed yet. It is in the schema's class list; no companion can be installed
   before N8.

## Alternatives rejected

- **Keep schema 1 and add keys.** Deployed clients ignore unknown keys, so this would not
  break them. It is rejected because schema 1's shape is one object per first-party
  component name with one `windows` block; publishers, per-platform assets and item classes
  do not fit it without a second, parallel structure in the same file.
- **Bump the schema number in place.** Every deployed `dxr-get` would treat the catalog as
  offline and stop fetching.
- **An app-store model with DisplayXR-hosted binaries and payment.** Rejected in §1.
- **Signed manifests per publisher, fetched separately, with no compiled index.** Each
  install would need several fetches and a second signature chain to check, and a client
  could be shown one publisher's old manifest next to another's new one. One compiled,
  signed, expiring index has one serial.
- **Reuse an existing package manager's manifest format** (winget, apt). They describe
  installers well and know nothing about component class, class ABI, registered ids,
  detection rules or licence state, which are the fields that make an item installable
  *correctly* here. Step 5 still installs `.deb` and `.pkg` files with the platform's tools.
